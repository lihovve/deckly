# План 3: модуль `data` — база, файлы штрихов, черновик, экспорт и импорт

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** хранение Deckly в открытой папке `/sdcard/Deckly/`:
- состояние колод в Room;
- штрихи — файлами;
- черновик редактора переживает убийство приложения;
- экспорт и импорт колоды одним JSON-файлом.

Всё это за портами в `domain`.

**Architecture:** `domain` получает интерфейсы репозиториев (порты), `data` их реализует. Room
хранит состояние алгоритма. Штрихи лежат бинарными файлами в `strokes/`, в базе только имя файла.
Корневая папка передаётся параметром, поэтому тесты идут на Robolectric во временной папке, без
планшета. Приложение (план 4) получает всё одной функцией `openDecklyData`.

**Tech Stack:**

- kotlinx-coroutines 1.11.0, kotlinx-serialization-json 1.12.0;
- тесты: Robolectric 4.17, JUnit 4.13.2, androidx.test core 1.7.0, kotlinx-coroutines-test 1.11.0.

## Global Constraints

- `data` зависит только от `domain` (проверяет `verifyModuleGraph`). `domain` по-прежнему без
  библиотек: порты — интерфейсы с `suspend`-функциями и типами из `domain` и `java.io`.
- Room 3.0.3, `AndroidSQLiteDriver`, `setJournalMode(TRUNCATE)`, не WAL. Схема экспортируется в
  `data/schemas/` и лежит в репозитории. Версия схемы — 1.
- Корень хранения — параметр `rootDir: File`. В приложении это
  `Environment.getExternalStorageDirectory()/Deckly`, в тестах — временная папка. База —
  `rootDir/deckly.db`, штрихи — `rootDir/strokes/`. Временные файлы — с расширением `.tmp`.
- Чужие файлы в `rootDir` (например `.git`) не трогаются никогда. Уборка работает только внутри
  `strokes/` и только с именами своего формата.
- Порядок записи содержимого карточки: новый файл под новым именем (сначала `.tmp`, потом
  переименование) → транзакция базы со ссылкой на него → удаление старого файла.
- Всё, что меняет один шаг движка (колода и её карточки), пишется одной транзакцией.
- Тесты `data`: JUnit 4 + Robolectric (`@RunWith(RobolectricTestRunner::class)`,
  `@Config(sdk = [35])`), `runTest`. Задача Gradle — `:data:testDebugUnitTest`.
- Имя метода начинается с глагола (правило владельца), конвертеры тоже: `mapDeck(entity)`, а не
  `entity.toDeck()`.
- После каждой задачи: `./gradlew :domain:test :data:testDebugUnitTest` и `./gradlew build` зелёные.
  Коммиты на русском, прямо в `main`, без пуша.

## Решения сверх архитектуры (мои, проверить при ревью)

1. **Формат файла штрихов** — бинарный, little-endian:
   - `DKS1` (4 байта ASCII), `int32` версия = 1;
   - затем две стороны, лицо и оборот. У каждой `int32` число штрихов, у штриха `float32` толщина,
     `int32` число точек и точки по `float32 x, y, pressure`.
   Один файл — обе стороны одной карточки. Бинарный, потому что карточка должна открываться быстрее
   200 мс.
2. **Имена файлов:** `card-<cardId>-<16 hex>.dks` для карточки и `draft-<16 hex>.dks` для черновика.
   16 hex — случайный суффикс, у каждой записи новое имя.
3. **Id карточек выдаёт счётчик** `app_state.next_card_id`, id не переиспользуются. Иначе id
   удалённой карточки, оставшийся в `tail`, мог бы достаться новой. Id колод — `AUTOINCREMENT`.
4. **Экспорт — только JSON, без zip** (ТЗ: «при желании в zip» — желания пока нет). Формат
   `"format": "deckly-deck"`, `"version": 1`. В `tail` пишутся только id карточек, которые есть в
   файле: удалённые карточки движок и так пропускает.
5. **Черновик правки удалённой карточки** при загрузке отбрасывается. Так бывает, если приложение
   убили между удалением карточки и удалением черновика.
6. **Повреждённый или пропавший файл штрихов** (например, неполная копия из резервной) —
   `StrokeFileException`, а не голый `EOFException`. Как это показать, решает план 4.

## Review Focus

1. Приложение убито между записью файла штрихов и транзакцией базы или между транзакцией и
   удалением старого файла. Ни одна карточка не теряет штрихи, а лишние файлы убираются при
   следующем открытии (задача 3).
2. Файл штрихов повреждён или пропал. `loadContent` бросает `StrokeFileException`, остальные карточки
   и колода открываются (задача 3).
3. Импорт обрезанного, мусорного, чужого JSON или файла новой версии. `ImportException` с верной
   причиной, а в базе и в `strokes/` после него ничего нового (задача 4).
4. Удаление колоды, в которой лежит черновик или которая выбрана текущей. Черновик и текущая колода
   сброшены, файлы её карточек удалены (задачи 2 и 3).
5. Уборка файлов не трогает чужое. `.git`, файлы вне `strokes/` и файлы с чужими именами внутри
   `strokes/` остаются на месте (задача 3).

### Task 6: повреждённая база не стирается

Испорченная копия при восстановлении была бы молча стёрта вместе со всеми колодами. Решение
владельца 4 ноября: такой файл не трогать, а приложение закрыть. Экран с сообщением и единственной

**Interfaces:**

    новая. Иначе:
    1. открыть через `SQLiteDatabase.openDatabase(file.path, null, OPEN_READWRITE, errorHandler)`,

    ложное «повреждена»;

### Task 7: уборка не удаляет то, что ещё можно спасти

Дефекты:
1. **Пропавшая или пустая `deckly.db` стирает весь `strokes/`.** Файл считается новой базой, Room
   создаёт пустую, а уборка удаляет все файлы штрихов. Это обрыв копии по MTP или ещё не
   скопированная база.
2. **Свежая база при несвежих штрихах.** Если копия снята посреди правки, база ссылается на новый
   файл, а в `strokes/` лежит старый. Уборка удаляет старый, и у карточки не остаётся ничего.
3. **Отключение питания:** переименование `.tmp` не сбрасывается на диск. После сбоя база
   ссылается на `card-X.dks`, а на диске `card-X.dks.tmp`. Уборка удаляет `.tmp`.

**Interfaces:**
- `class DatabaseMissingException(val dir: File, val cardFileCount: Int) : IOException`.
  `openDecklyData` бросает его до создания базы, если `deckly.db` нет или он пустой, а в `strokes/`
  есть хотя бы один `card-*.dks`. Ни база, ни файлы не трогаются. План 4 обрабатывает его так же,
  как `DatabaseDamagedException`: сообщение и «Закрыть».
- Новые правила `cleanUpStrokeFiles`. Входные данные: ссылки карточек `id → content_file`, ссылка
  черновика и `next_card_id`.
  - `X.tmp`: если `X` есть в ссылках, а файла `X` нет, переименовать `X.tmp` в `X`. Файл полный:
    `fsync` был до переименования, а оно — до транзакции. Иначе удалить.
  - `card-<id>-*.dks` удаляется только в двух случаях:
    - карточка `<id>` есть в базе, ссылается на другой файл, и тот файл существует (старая версия);
    - карточки `<id>` нет в базе, и `id < next_card_id` (удалённая карточка или неудавшееся
      создание).
    Во всех остальных случаях файл остаётся: `id >= next_card_id` при несвежей базе, или файл
    по ссылке пропал.
  - `draft-*.dks` удаляется, если строки черновика нет, или если она ссылается на другой файл и тот
    существует.
- Запасное чтение:
  - пропал файл по ссылке → `loadContent` читает самый новый по `lastModified` из оставшихся
    `card-<id>-*.dks` этой карточки;
  - если нет ни одного → `StrokeFileException`, как раньше;
  - `loadDraft` при пропавшем файле читает самый новый `draft-*.dks`. Если нет и его или файл
    повреждён, строка черновика удаляется и возвращается `null`: без этого падал бы каждый запуск.
- `StrokeFiles` после `renameTo` сбрасывает на диск саму папку `strokes/`:
  `syncDirectory: (File) -> Unit`. По умолчанию это `FileChannel.open(dir.toPath(), READ).use { it.force(true) }`,
  в тестах можно подменить.
